# 协作协议

所有成员共用本协议。约束的是席位，不是成员：谁坐这个席位就守这一节。详细推理和执行过程留在各自的原生会话，公共文件只写结论、依据要点和位置。

## 1. 总则

### 文件与用途

| 文件 | 用途 | 何时读 |
|---|---|---|
| `PROGRESS.md` | 唯一入口：下一步、现状、生效决议、目标表、任务表、卡点、加载地图 | 每次 |
| `协议.md` | 本协议 | 按加载地图读相关一节 |
| `日志.md` | 每天的决议、任务流转和方向变化 | 收工时写；查历史时搜索 |
| `成员.md` | 有哪些成员、型号、能力表、唤醒和续接方式（由班子配置生成） | 选人、派活时 |
| `运行记录/` | 派活脚本自动写入的每次派活记录，供看板读取，不手改 | 查某次派活的结果时 |
| `决议.md` | 生效决议全文 | 任务卡引用或要改方向时 |
| `议题/I00x-*.md` | 朝会：需要多个成员分别发表观点的讨论 | 开朝会、写总结或裁决时 |
| `目标/G00x-*.md` | 目标卡：要什么、总裁批准的流程 | 新目标、改流程，或做属于它的任务时 |
| `任务/T00x-*.md` | 任务卡：流转、交接 | 被点名时 |
| `经验.md` | 可复用的做法和坑 | 开始同类工作前 |
| `归档/` | 已关闭的议题、目标和任务，被取代的决议 | 查历史时，先搜索 |

### 基本规则

1. 只读加载地图要求的文件；需要历史时先搜索，再读命中部分。
2. 修改任何公共文件前重新读取它，只改属于自己的分区，不改写他人内容。
3. 讨论中的意见不是决议。只有总裁确认后写入 `决议.md` 的才是。
4. 不确定的结果写「未知」或「未验证」，不能推断为完成。
5. 不在公共文件中粘贴大段过程、日志或代码，写位置即可。
6. 忠于目标：区分硬约束和可替换的做法；有更合适的方案就说明依据与取舍；可以反对、报告失败和不确定，不为顺从而隐藏问题。
7. 路径：协作文件直接写文件名（都在 `collab/` 下）；其他项目文件，链接写 `../路径`，反引号里写相对项目根的路径。

## 2. 席位

席位随任务或目标流程指定，同一成员在不同任务里可以坐不同席位。成员能做什么（权限、型号）看 `成员.md`；行为边界看任务卡的「硬约束」「授权」。

### 总裁
- 定方向，批准总管的分析和整体框架，确认决议，裁决议题，授权超出已批准框架的事。
- 写「▶ 下一步」和议题「裁决」；说"定了"的事才进 `决议.md`。

### 总管
1. **先批准，后派发**：收到任务后先给总裁分析和整体框架——目标与成功标准、步骤、谁做、在哪里验收由谁验、预计成本。**总裁明确同意前，一律不派发**。
2. **框架内自主**：框架批准后，执行中的问题由总管自己解决——调整步骤、换人、返工、补任务都可以，在流转里写明原因即可。只有「上报」一节所列的绝对阻塞才上报总裁。
3. **用人不疑**：默认相信成员自己完成的任务，不逐个任务交叉验证；验收放在目标层面（见「验收」）。
4. **复用会话**：同一个目标里尽量续接已有的执行者会话，不另开新会话（见「派活」）。
5. **验收**：默认由总管自己按目标的成功标准验收；只有总裁在批准框架时同意了第三方验收，才派其他成员验。
6. **把关改进**：验收者提出的返工和改进，由总管决定是否采纳。
7. **汇报**：先写现状和要总裁决定的事；过程和证据放在卡里，写位置。
8. **维护「待你决定」**：PROGRESS「待你决定」只由总管写，放两类事：一是下级报上来的阻塞或重大问题，总管先判断、整理好方案再写；二是和总裁讨论最初问题、定框架时遇到的需要拍板的点（如批准框架、方案取舍）。每条以类型开头（批准框架 / 受阻 / 裁决 / 返工 / 授权），写清可选方案与代价和总管建议。总裁拍板后，总管把结果记入流转或决议，删掉这一条，日志记一行。

### 执行
1. 开工先在流转写「执行中」；不能不给结论就停止，结束时只能是「待验收」或「受阻」。
2. 交付时写清做了什么、自测结果和证据位置；可复核的原始输出写成文件。
3. 遇到问题先报总管（在任务卡流转写明）；不直接写「待你决定」，总管处理不了的由总管按「上报」处理。

### 验收
1. 以目标为准：总目标和成功标准达到即判「通过」，不因还能做得更好而不通过。
2. 只提真正影响结果的问题。改进建议可以写在验收结论里，但不作为通过的条件；要返工或改进，由总管同意后才进行。
3. 像使用者一样试用交付物：能跑的跑，能打开的打开，不只核对文字。
4. 结论写清核查了什么、证据位置、未覆盖项。
5. 第三方验收者不能是执行者本人，开新会话，只依据目标卡、交付物和流转判断。验收意见由验收者本人写，总管不改写。

### 与会者（朝会）
- 只看派活脚本给的内容；第 1 轮只有「问题」「与会」。按指定视角发言，每轮 ≤400 字。

## 3. 流程

### 目标与流程
- 总管起草目标卡（状态「待批准」）和整体框架，给总裁看；总裁明确同意后改「进行中」，才能派发。属于目标的任务在卡头写「目标」「阶段」，并把编号填进流程表「子任务」列。
- 流程表只写需要的阶段，最后一步是目标验收和汇报。各任务不单独设验收阶段。
- 阶段进度由子任务推出：某阶段的子任务全部通过，该阶段才算通过；后一阶段要等前面的阶段都通过才开始。不手写阶段状态。
- 框架内的调整（增删、拆分步骤，换人，返工，补任务）由总管决定，在流程表「变更」追加一行并写明原因。
- 改目标、成功标准、硬约束，或改验收结构（如加、撤第三方验收），要总裁批准。
- 用派活脚本时，它会按流程表检查顺序和人选；确需偏离时加 `--override "理由"`，理由记入运行记录，看板标为偏离。

### 多个目标
- 同时「进行中」的目标不超过 3 个；再多的留在「待批准」或改「暂停」。成员是共用的，同时开太多每个都慢。
- 目标卡头写「优先」（1 最高），由总裁定；资源冲突时（如两个目标都要同一成员），总管按优先顺序排。
- 目标之间有先后时，卡头写「依赖：G00x」；前置目标没完成前，这个目标不派发。
- 每张任务卡只属于一个目标；不属于任何目标的零碎任务，「目标」写「—」。
- 会话复用以目标为界：同一目标内续接，跨目标另开新会话。
- 「待你决定」每条的编号写目标或任务号，看板按目标归类。
- 目标验收通过后，总管把结论（第三方验收用原文）写进「待你决定」，总裁批准后目标卡改「完成」并移到 `归档/目标/`。

### 派活
- **前提**：所属目标或这批派活的框架已获总裁明确同意。
- **选人**：流程表或任务卡已写人选的照办。没写的由总管按 `成员.md`「能力表」选：先定难度，简单的（整理、格式、批量、查资料）用能胜任的最便宜的成员，中等用 B 档，难或关键的用 A 档。同一人连续两次返工：升一档续做，在流转里写明原因。
- **身份**：成员都是通用型，身份由总管按任务写在卡上（任务卡「身份」、议题「与会」的视角）。
- **复用会话**：同一个目标里，后续任务、返工、追问优先续接已有的执行者会话，让它带着上下文继续。只有这些情况才开新会话：第三方验收、朝会第 1 轮、换了一件无关的事、上下文已经太长（新会话的启动语交代要点）、成员权限改过（会话权限在开会话时定）。
- **权限**：由班子配置决定，写在 `成员.md`；任务卡只写行为边界。

### 状态流转
- 任务：已交接 → 执行中 → 待验收 → 通过 / 需补充；任何时候可转为「受阻：原因」。通过即结束。
- 每次变化由经办人在卡内「流转」加一行：经办人是这一步谁做的，接手人是下一步归谁。最后一行的接手人就是当前负责人，结束写「—」。改派也加一行「已交接」，写明原因。
- 同步卡头「状态」和 PROGRESS「任务」表。
- 总裁在对话里做的、影响任务的决定（选方案、改方向、放行、叫停），由总管在该任务卡「流转」记一行：经办人写「总裁」，说明写决定内容和原话要点。看板的泳道流程按流转画，不记就看不到这一步。
- 执行者写：执行中、待验收、受阻。任务的「通过」由总管确认交付写下（默认相信执行者的自测，不另行交叉验证）；要返工时总管写「需补充」并说明。

### 验收
验收在目标层面做，不逐个任务做。

| 层面 | 默认 | 例外 |
|---|---|---|
| 任务 | 用人不疑：执行者交付并自测，总管确认交付即「通过」 | 无 |
| 目标 | 总管按目标的成功标准验收 | 总裁在批准框架时同意第三方验收，才派其他成员验；对外交付、不可逆或方向性的结果由总裁拍板 |

- 只要总目标和成功标准达到就算通过。
- 改进建议可以保留在结论里（真正影响结果的才写）；返工和改进必须总管同意。

### 上报
框架批准后，总管在框架内自主解决问题，只有以下绝对阻塞才在 PROGRESS「待你决定」追加一条（类型写「受阻」），并把相关任务标为受阻：
- 要改目标、成功标准、硬约束或验收结构
- 需要只有总裁能给的东西：授权、账号或登录、付费、不可逆操作的许可
- 与生效决议冲突，或证据推翻了决议的前提
- 总管穷尽办法仍无法推进

### 收工清单
1. `日志.md` 写今天的决议、任务流转和方向变化。
2. 更新 PROGRESS「现状」「▶ 下一步」「卡点 / 待你决定」。
3. 通过的任务：卡片移到 `归档/任务/`，从「任务」表删行，编号记入「已完成」。总裁批准完成的目标：卡片移到 `归档/目标/`，从「目标」表删行。
4. 已裁决的议题：结论写入决议，文件移到 `归档/议题/`。
5. 不再约束当前工作的决议，从「生效决议」删去（全文留在 `决议.md`）。

## 4. 朝会

需要多个成员分别发表观点时开朝会。

1. 立题：总管复制 `议题/_模板.md`，写「问题」（要决定什么、背景与约束、参考资料、已知选项）和「与会」（成员及视角）。与会者尽量来自不同应用或型号。
2. 召集：派活脚本 `meet I00x` 开下一轮。第 1 轮各与会者开新会话、并行发言、互不可见；之后各轮续接自己的会话，读到全部上一轮发言后回应分歧，修正或坚持。最多 3 轮，没有实质分歧就不再加轮。
3. 发言原文由脚本写进各轮，总管不改写。
4. 总结：总管写「总结」——共识、争议（各方立场、依据、代价）、总管建议；在 PROGRESS「待你决定」加一行，议题状态改「待裁决」。
5. 裁决：总裁写「裁决」，结论写入决议，需要的后续开目标或任务；议题状态改「已裁决」，文件移到 `归档/议题/`。保留的异议可写进新议题。

议题状态：开放 → 第1轮 → 第2轮 →（第3轮）→ 待裁决 → 已裁决

## 5. 记录规范

### 写入规则

| 位置 | 谁写 | 方式 | 上限 |
|---|---|---|---|
| PROGRESS「现状」 | 完成一步的成员 | 覆盖自己相关的行 | ≤5 行，每行 ≤80 字 |
| PROGRESS「目标」表 | 总管（总裁批准后） | 一个目标一行，按优先排；状态只写 待批准 / 进行中 / 暂停 / 完成 / 取消 | 进行中 ≤3 个 |
| PROGRESS「任务」表 | 状态变化的当事人 | 同步卡头状态；「验收结论」列由总管或第三方验收者写 | — |
| PROGRESS「▶ 下一步」 | 总裁，或收工时代写 | 覆盖 | 1 条 |
| PROGRESS「生效决议」 | 写决议的成员 | 每条一行 | 只列仍约束当前工作的 |
| PROGRESS「卡点 / 待你决定」 | 总管（成员的问题先报总管） | 总裁拍板后总管删除，结果记入流转或决议，日志记一行 | 只放未解决的；每条以类型开头 |
| `日志.md` | 收工的成员 | 新的在上，一行一条 | 每天 ≤5 条，每条 ≤60 字 |
| 议题「问题」「与会」「总结」 | 总管 | 问题和与会开会前写好、开会后不改；总结各轮结束后写一次 | — |
| 议题各轮 | 派活脚本 `meet` | 写入发言原文，标明成员、视角和派活编号；不手改 | 每人每轮 ≤400 字 |
| 议题「裁决」 | 总裁（可代写，需总裁确认） | 填写一次 | — |
| `决议.md` | 总裁说"定了"之后 | 新增条目，不改旧条目 | — |
| 目标卡「要什么」「流程」「验收」 | 总管起草，总裁批准 | 框架内的调整由总管在「变更」追加一行；改目标、成功标准、硬约束、验收结构要总裁批准 | — |
| 目标卡「子任务」列 | 派发人 | 新建子任务时填编号 | — |
| 任务卡「交接」 | 派发人 | 交接时填好；总裁确认后不改 | 超过 10 行的规格写进项目文档再链接 |
| 任务卡「流转」 | 经办人；总裁的决定由总管代记（经办人写「总裁」） | 追加一行，写明接手人 | 说明 ≤60 字，证据写位置 |
| 任务卡「备注」 | 执行者或验收者 | 追加，标明日期和经办人 | 长内容写成文件放链接 |
| `成员.md` | 班子配置生成（`init.sh team-sync`） | 只手写「本项目补充」一节 | — |
| `经验.md` | 任何成员 | 一条一行 | ≤20 条，超出就合并 |

### 编号
- 议题 `I001`、目标 `G001`、任务 `T001`、决议 `D001`，各自递增，不复用。
- 新编号 = 在 `collab/`（含 `归档/`）中搜索到的最大编号 + 1。
- 新建议题、目标或任务：复制对应目录下的 `_模板.md`，命名为 `编号-简短主题.md`，并在 PROGRESS 对应的表加一行。

### 原生会话记录
流转说明末尾和决议来源中写明：`应用「会话名」日期`，例如 `Codex「T003 接口实验」10-18`。没有会话名时写能找到它的信息。

### 决议变更
决议不改原文。新决议注明「取代：D00x」，PROGRESS 中替换对应行，旧条目整段移到 `归档/决议.md`。
