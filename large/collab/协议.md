# 协作协议

所有成员共用本协议。约束的是席位，不是成员：谁坐这个席位就守这一节。详细推理和执行过程留在各自的原生会话，公共文件只写结论、依据要点和位置。

## 1. 总则

### 文件与用途

| 文件 | 用途 | 何时读 |
|---|---|---|
| `PROGRESS.md` | 唯一入口：下一步、现状、生效决议、目标表、任务表、卡点、加载地图 | 每次 |
| `协议.md` | 本协议 | 按加载地图读相关一节 |
| `日志.md` | 每天的决议、任务流转和方向变化 | 收工时写；查历史时搜索 |
| `成员.md` | 有哪些成员、型号、能力表、唤醒和续接方式（由班子配置生成） | 选人、派活时 |
| `运行记录/` | 派活脚本自动写入的每次派活记录，供看板读取，不手改 | 查某次派活的结果时 |
| `决议.md` | 生效决议全文 | 任务卡引用或要改方向时 |
| `议题/I00x-*.md` | 朝会：需要多个成员分别发表观点的讨论 | 开朝会、写总结或裁决时 |
| `目标/G00x-*.md` | 目标卡：要什么、总裁批准的流程 | 新目标、改流程，或做属于它的任务时 |
| `任务/T00x-*.md` | 任务卡：流转、交接 | 被点名时 |
| `经验.md` | 可复用的做法和坑 | 开始同类工作前 |
| `归档/` | 已关闭的议题、目标和任务，被取代的决议 | 查历史时，先搜索 |

### 基本规则

1. 只读加载地图要求的文件；需要历史时先搜索，再读命中部分。
2. 修改任何公共文件前重新读取它，只改属于自己的分区，不改写他人内容。
3. 讨论中的意见不是决议。只有总裁确认后写入 `决议.md` 的才是。
4. 不确定的结果写「未知」或「未验证」，不能推断为完成。
5. 不在公共文件中粘贴大段过程、日志或代码，写位置即可。
6. 忠于目标：区分硬约束和可替换的做法；有更合适的方案就说明依据与取舍；可以反对、报告失败和不确定，不为顺从而隐藏问题。
7. 路径：协作文件直接写文件名（都在 `collab/` 下）；其他项目文件，链接写 `../路径`，反引号里写相对项目根的路径。

## 2. 席位

席位随任务或目标流程指定，同一成员在不同任务里可以坐不同席位。成员能做什么（权限、型号）看 `成员.md`；行为边界看任务卡的「硬约束」「授权」。

### 总裁
- 定方向，批准目标和流程，确认决议，裁决议题，授权超出任务卡范围的事。
- 写「▶ 下一步」和议题「裁决」；说"定了"的事才进 `决议.md`。

### 总管
1. 拆任务、写目标卡和任务卡、选人派活、主持朝会、整合结果、维护 PROGRESS。不验收自己统筹的活（自检档的抽查除外，见「验收」）。
2. 开跑一个目标或一批派活前，先给总裁看整体流程：步骤、谁做、哪几步验收及理由、预计成本。总裁点头后再派。
3. 验收按风险提出，不是每张卡都验：用「验收」一节的三问定档，写进卡头「验收方式」。
4. 续接还是重开会话按「派活」一节判断，并在流转说明里写明。
5. 汇报先写现状和要总裁决定的事；过程和证据放在卡里，写位置。

### 执行
1. 开工先在流转写「执行中」；不能不给结论就停止，结束时只能是「待验收」或「受阻」。
2. 交付前按验收标准自测一遍，把可复核的原始输出写成文件，在流转里写位置，免得验收来回要证据。
3. 超出授权、与决议冲突或无法解决的阻塞，按「上报」处理。

### 验收
1. 不能是执行者本人；独立验收还不能是总管。独立验收开新会话，只依据卡上的依据、目的、验收标准、授权和交付物判断，不读执行者的自我评价。
2. 像使用者一样试用交付物：能跑的跑，能打开的打开，不只核对文字。
3. 只有影响目标或验收标准的问题才判「需补充」；小问题判「通过」，在验收结论里附建议。
4. 结论写清核查了什么、证据位置、未覆盖项。验收意见由验收者本人写，总管不改写。

### 与会者（朝会）
- 只看派活脚本给的内容；第 1 轮只有「问题」「与会」。按指定视角发言，每轮 ≤400 字。

## 3. 流程

### 目标与流程
- 目标由总管起草（状态「待批准」），连同整体流程给总裁看，批准后改「进行中」。属于目标的任务在卡头写「目标」「阶段」，并把编号填进流程表「子任务」列。
- 流程表只写需要的阶段。各子任务已按「验收方式」验过的，不再另设「目标整体验收」阶段；总裁要求时才加。
- 阶段进度由子任务推出：某阶段的子任务全部通过，该阶段才算通过；后一阶段要等前面的阶段都通过才开始。不手写阶段状态。
- 同一席位换人：总管决定，在相关任务的流转里写明原因。
- 增删阶段、调换顺序、改通过条件：写进「待你决定」，总裁批准后改流程表并在「变更」追加一行。
- 用派活脚本时，它会按流程表检查顺序和人选；确需偏离时加 `--override "理由"`，理由记入运行记录，看板标为偏离。
- 最后由总管把各阶段结论（验收结论用原文）写进「待你决定」，总裁批准后目标卡改「完成」并移到 `归档/目标/`。

### 派活
- **选人**：流程表或任务卡已写人选的照办。没写的由总管按 `成员.md`「能力表」选：先定难度，简单的（整理、格式、批量、查资料）用能胜任的最便宜的成员，中等用 B 档，难或关键的用 A 档。同一人连续两次「需补充」：升一档续做，在流转里写明原因。关键任务的验收者档位不低于执行者，尽量用与执行者不同的应用。
- **身份**：成员都是通用型，身份由总管按任务写在卡上（任务卡「身份」、议题「与会」的视角）。
- **续接还是重开**：同一件事返工、追问、补充，续接原会话；独立判断（验收、朝会第 1 轮）、换一件事、上下文已经太长，开新会话，并在启动语里交代要点。会话权限在开会话时定，改了成员权限后要开新会话。
- **权限**：由班子配置决定，写在 `成员.md`；任务卡只写行为边界。

### 状态流转
- 任务：已交接 → 执行中 → 待验收 → 通过 / 需补充 / 未通过；任何时候可转为「受阻：原因」。通过即结束。
- 每次变化由经办人在卡内「流转」加一行：经办人是这一步谁做的，接手人是下一步归谁。最后一行的接手人就是当前负责人，结束写「—」。改派也加一行「已交接」，写明原因。
- 同步卡头「状态」和 PROGRESS「任务」表。
- 执行者写：执行中、待验收、受阻。验收者（自检档为总管）写：通过、需补充、未通过。

### 验收
总管派活时用三问定档，写进卡头「验收方式」：谁做的？出错能否低成本回退？错误是否容易被发现？

| 档 | 什么时候用 | 怎么验 |
|---|---|---|
| 自检 | 默认。小而可回退、错了容易发现的活 | 执行者按验收标准自测并留原始输出；总管抽查后写「通过」或「需补充」 |
| 独立验收 | 关键、难回退或错误不易发现的活 | 另一成员开新会话按「席位 · 验收」验 |
| 需总裁批准 | 对外交付、不可逆操作、方向性结果 | 总管汇总给总裁，总裁点头即通过 |

### 上报
遇到以下情况，在 PROGRESS「待你决定」追加一条，并把相关任务标为受阻：
- 超出任务卡授权范围
- 与生效决议冲突，或证据推翻了决议的前提
- 无法自行解决的阻塞

### 收工清单
1. `日志.md` 写今天的决议、任务流转和方向变化。
2. 更新 PROGRESS「现状」「▶ 下一步」「卡点 / 待你决定」。
3. 通过的任务：卡片移到 `归档/任务/`，从「任务」表删行，编号记入「已完成」。总裁批准完成的目标：卡片移到 `归档/目标/`，从「目标」表删行。
4. 已裁决的议题：结论写入决议，文件移到 `归档/议题/`。
5. 不再约束当前工作的决议，从「生效决议」删去（全文留在 `决议.md`）。

## 4. 朝会

需要多个成员分别发表观点时开朝会。

1. 立题：总管复制 `议题/_模板.md`，写「问题」（要决定什么、背景与约束、参考资料、已知选项）和「与会」（成员及视角）。与会者尽量来自不同应用或型号。
2. 召集：派活脚本 `meet I00x` 开下一轮。第 1 轮各与会者开新会话、并行发言、互不可见；之后各轮续接自己的会话，读到全部上一轮发言后回应分歧，修正或坚持。最多 3 轮，没有实质分歧就不再加轮。
3. 发言原文由脚本写进各轮，总管不改写。
4. 总结：总管写「总结」——共识、争议（各方立场、依据、代价）、总管建议；在 PROGRESS「待你决定」加一行，议题状态改「待裁决」。
5. 裁决：总裁写「裁决」，结论写入决议，需要的后续开目标或任务；议题状态改「已裁决」，文件移到 `归档/议题/`。保留的异议可写进新议题。

议题状态：开放 → 第1轮 → 第2轮 →（第3轮）→ 待裁决 → 已裁决

## 5. 记录规范

### 写入规则

| 位置 | 谁写 | 方式 | 上限 |
|---|---|---|---|
| PROGRESS「现状」 | 完成一步的成员 | 覆盖自己相关的行 | ≤5 行，每行 ≤80 字 |
| PROGRESS「目标」表 | 总管（总裁批准后） | 一个目标一行，只写 待批准 / 进行中 / 完成 / 取消 | — |
| PROGRESS「任务」表 | 状态变化的当事人 | 同步卡头状态；「验收结论」列只由验收者写 | — |
| PROGRESS「▶ 下一步」 | 总裁，或收工时代写 | 覆盖 | 1 条 |
| PROGRESS「生效决议」 | 写决议的成员 | 每条一行 | 只列仍约束当前工作的 |
| PROGRESS「卡点 / 待你决定」 | 任何成员追加 | 解决后由解决者删除，日志记一行 | 只放未解决的 |
| `日志.md` | 收工的成员 | 新的在上，一行一条 | 每天 ≤5 条，每条 ≤60 字 |
| 议题「问题」「与会」「总结」 | 总管 | 问题和与会开会前写好、开会后不改；总结各轮结束后写一次 | — |
| 议题各轮 | 派活脚本 `meet` | 写入发言原文，标明成员、视角和派活编号；不手改 | 每人每轮 ≤400 字 |
| 议题「裁决」 | 总裁（可代写，需总裁确认） | 填写一次 | — |
| `决议.md` | 总裁说"定了"之后 | 新增条目，不改旧条目 | — |
| 目标卡「要什么」「流程」 | 总管起草，总裁批准 | 批准后改流程见「目标与流程」，在「变更」追加一行 | — |
| 目标卡「子任务」列 | 派发人 | 新建子任务时填编号 | — |
| 任务卡「交接」 | 派发人 | 交接时填好；总裁确认后不改 | 超过 10 行的规格写进项目文档再链接 |
| 任务卡「流转」 | 经办人 | 追加一行，写明接手人 | 说明 ≤60 字，证据写位置 |
| 任务卡「备注」 | 执行者或验收者 | 追加，标明日期和经办人 | 长内容写成文件放链接 |
| `成员.md` | 班子配置生成（`init.sh team-sync`） | 只手写「本项目补充」一节 | — |
| `经验.md` | 任何成员 | 一条一行 | ≤20 条，超出就合并 |

### 编号
- 议题 `I001`、目标 `G001`、任务 `T001`、决议 `D001`，各自递增，不复用。
- 新编号 = 在 `collab/`（含 `归档/`）中搜索到的最大编号 + 1。
- 新建议题、目标或任务：复制对应目录下的 `_模板.md`，命名为 `编号-简短主题.md`，并在 PROGRESS 对应的表加一行。

### 原生会话记录
流转说明末尾和决议来源中写明：`应用「会话名」日期`，例如 `Codex「T003 接口实验」10-18`。没有会话名时写能找到它的信息。

### 决议变更
决议不改原文。新决议注明「取代：D00x」，PROGRESS 中替换对应行，旧条目整段移到 `归档/决议.md`。
