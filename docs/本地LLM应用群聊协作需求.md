# 本地 LLM 应用群聊协作需求

版本：第二版  
日期：2026 年 10 月 2 日  
用途：明确 AI 公司的管理框架、产品目标、协作流程、核心约束与首版范围，供后续技术调研和开发使用。

## 产品目标

建立一个由用户主导的小型 AI 公司，以轻量群聊连接本地成熟 LLM 应用中的真实助手会话。用户兼任董事长与 CEO，主要关注战略目标、优先级、资源投入和重大取舍；Codex、Claude、Antigravity 等少数助手承担部门职责，与用户共同确定方案、任务分工和验收负责人。方案确定后，各助手回到自己的原生应用中执行；群聊接收结果与验收结论。

可以借鉴现有项目，也可以自行开发协调工具。核心要求是依靠原生应用完成思考与执行，保留其完整能力和可追溯会话。群聊负责共同上下文、发言控制、任务交接和结果反馈，不承担详细执行过程。

本文区分已明确需求与建议默认值。应用是否允许接入原生会话、如何保留完整能力，是后续需要验证的技术问题，不能作为已实现能力。

## AI 公司的管理框架

采用“战略委员会、任务负责人制、独立验收”的组织方式。用户与相关助手组成战略讨论小组；每项任务指定一个对交付负责的负责人，并明确执行者和验收者。组织保持少数成员，不为模拟传统公司而增加管理层级。

一个成熟 LLM 应用可以承担相当于一个部门的工作范围，这是组织设计目标；实际承载能力仍通过交付和验收判断。组织的基本单位是具有明确职责、持续上下文和成果记录的原生会话。无需永久规定某种模型只能管理或只能执行，角色可以随任务调整。

### 战略意图与自主执行

借鉴 Mission Command（任务式指挥）：用户明确任务目的、期望结果和授权边界，负责人在边界内自主选择执行方法。用户无需逐步指导搜索、编辑、编程或工具操作。

任务交接必须让负责人理解：为什么做、交付什么、有哪些限制、谁负责、谁验收，以及什么情况下必须回来请示。完整原生能力服务于自主执行，不代表助手可以自行扩大目标或授权范围。

### 战略与部门行动对齐

借鉴 Hoshin Kanri（方针管理）与 Catchball（上下往返讨论）：用户提出战略方向，成员提出可行路线、资源需求和约束，经过有限讨论后由用户敲定方案。每项任务关联一个战略目标，能说明其对目标的贡献。

建议初期同时推进两到三个战略主题，作为减少协调负担的默认值，而非系统硬限制。成员发现执行证据推翻战略假设时，应把证据带回群聊，由用户决定是否调整方向。

### 分级授权与例外上报

借鉴可逆决策与难以逆转决策的区分：授权范围内的日常、可撤销执行决策由负责人处理；改变战略目标、显著增加资源投入或超出授权范围的决定回到用户。

| 决策层级 | 决策者 | 内容 |
| --- | --- | --- |
| 战略决策 | 用户 | 选择项目、确定目标与优先级、资源投入及重大范围变化 |
| 任务决策 | 获授权的负责人 | 分配已确认工作、协调依赖、安排授权范围内的返工 |
| 执行决策 | 执行者 | 在任务边界内选择方法、工具和具体实现 |
| 验收判断 | 指定验收者 | 按既定标准判断成果是否合格，说明证据与缺口 |

执行者仅在目标冲突、超出授权、关键假设被推翻或存在无法自行解决的阻塞时，上报需要决定的问题。普通执行细节保留在原生应用。用户日常主要查看成果和待决事项。

### 独立判断与明确责任

每项任务有一个明确的交付负责人，参与者可以有多个。负责人不能通过“已经转交其他成员”免除交付责任；协调负责人负责交接和缺口跟踪，但不替代执行者与验收者的判断。

重要任务由另一个成员验收，执行者自报完成不能直接关闭任务。任务负责人、执行者和验收者可以是不同成员，也可按任务规模适当合并职责；关键成果保留独立验收。

讨论阶段允许提出反对意见，并要求说明依据、假设和未知事项。用户裁决后，成员按确定的方案执行；保留异议不阻止履行分工。出现新证据或触发上报条件时，可以重新提出议题。不能以反复讨论或多数附和代替用户裁决和成果证据。

### 战略会议与执行闭环

默认会议流程为：提出问题 → 各成员独立给出判断 → 第二轮回应分歧 → 用户裁决 → 指定负责人、执行者和验收者 → 原生应用执行 → 结果回报 → 验收或返工。

“每人最多两次”可用于第一轮给方案与依据、第二轮回应质疑。独立判断指先形成自身判断再回应他人；是否技术上隐藏其他人的第一轮回答，属于后续交互选择。讨论、执行反馈和验收反馈分别处理，避免会议额度影响任务交付。

可以用“朝议、决议、承办、复核、奏报”理解这个流程：用户提出方向并裁决，助手讨论后承办，另一成员复核，最后回报结果。这只是交互比喻，不要求复制古代官制或建立额外层级。

### 最小管理记录

系统只需维护战略目标、公共讨论、正式决议、任务交接和验收结果五类核心内容。它们可以直接附着在群聊与少量任务记录中，不必成为五个复杂独立模块。

正式决议记录目标、选择的方案、主要取舍和分工；任务交接关联决议与原生会话；验收结果关联具体成果。详细执行过程继续留在各应用中。

## 使用场景

用户提出：“我们讨论这个研究问题，先确定调研计划。Codex、Claude、Antigravity 轮流分析，每人最多回复两次。”

三个助手根据共同群聊上下文分析目标、路线和分歧。用户参与讨论并敲定计划，指定 Codex 执行调研、Claude 负责验收，以及 Antigravity 是否承担独立任务。

Codex 在原生应用中的任务会话里开展调研。搜索过程、工具调用、材料分析和中间草稿留在该会话中。完成后，Codex 在群里发布简明结果和成果位置，并 `@Claude`。

Claude 按已确定的标准，在自己的工具中检查成果，随后在群里反馈“通过”“需要补充”或“未通过”，说明依据并通知相关成员。需要调整顶层方案时，再回到群聊讨论；具体返工仍在执行者自己的工具中完成。

## 产品边界

| 群聊承担 | 原生应用承担 |
| --- | --- |
| 目标与约束讨论 | 文件操作、搜索、代码运行及其他具体工作 |
| 顶层方案分析与决策 | 执行中的详细分析、工具调用和中间过程 |
| 共同讨论上下文 | 原生会话历史、配置、工具与权限 |
| 发言对象、顺序和次数控制 | 任务执行及独立验收 |
| 分工、任务交接及责任归属 | 成果生成、修改和验证 |
| 结果摘要、阻塞说明和验收结论 | 可追溯的完整执行记录 |

群聊可以有统一界面和少量本地协调状态，但不需要重建代码编辑器、浏览器、终端、模型服务或原生工具体系。首版不需要复杂项目看板、自动规划平台或完整执行日志聚合。

## 成员与角色

群成员绑定到具体的应用和会话，而不是只绑定到模型名称。需要能区分同一应用中的不同会话，例如“Codex 调研负责人”和“Codex 独立审查”。

| 角色 | 职责与权限 |
| --- | --- |
| 用户 | 兼任董事长与 CEO，负责战略、资源取舍、最终裁决和角色授权，随时暂停或接管 |
| 讨论成员 | 在被指定或轮到自己时分析与回答 |
| 协调负责人 | 整理决议、交接任务、追踪缺口和汇总待决事项；不因协调职责自动获得指挥权 |
| 指挥负责人 | 在用户授予的范围内，把已确定的任务交给成员，并协调反馈与返工 |
| 任务负责人 | 对一项任务的最终交付负责，协调参与者并确保结果进入验收 |
| 执行者 | 在原生应用中完成任务，回报结果或必要的阻塞 |
| 验收负责人 | 在自己的工具中核验成果，回报结论与依据 |

角色按议题或任务指定，同一成员可以在不同任务中承担不同角色。拥有发言资格不自动获得派发任务的权限。用户保留最终控制权；助手执行仍遵循原生应用已有的权限与确认机制。

## 核心功能需求

### 原生会话连接

- 能将本地 Codex、Claude、Antigravity 等应用的指定会话加入群聊；这三类应用是目标范围，接入顺序由可行性调研决定。
- 展示成员名称、所属应用、会话标识及基本连接状态，避免任务进入错误会话。
- 支持从成员或任务记录定位原生会话；若无法提供直接跳转，应给出可用的定位信息。
- 保留原生应用的上下文、模型与设置、指令、skills、工具、插件、登录、工作目录、执行主机和权限流程。
- 不能以“使用同一个账号或模型”代替能力等价验证，也不能将独立 CLI 调用默认为等价接入。
- 对尚未验证或缺失的能力明确标注；接入失败时不能静默改用另一个执行环境。

完整利用原生应用能力是产品的核心验收条件，不意味着每次回答的措辞或执行结果必须完全相同。

### 共同群聊上下文

- 成员回答时能够获得当前议题的公共消息、已经确认的方案、分工和验收标准。
- 公共群聊内容不等于成员原生应用的全部历史；无需自动汇集所有私有聊天和执行记录。
- 派发任务时，将相关公共上下文与已确认任务要求交给执行会话。
- 首版优先采用清晰的公共消息与方案记录。长对话摘要或压缩可以后续增加，但不能丢失用户约束和已确认决定。

### 指定回答与轮替讨论

- 用户可 `@` 指定一个或多个成员回答。
- 支持指定顺序的轮替分析，以及按成员设置发言上限，例如每人最多两次。
- 未被指定且未轮到的成员保持等待；达到上限后停止自动发言。
- 用户可暂停、结束、调整顺序或追加次数。
- 顺序和次数限制由协调层控制，不能只依赖提示词约定。

建议默认值：次数按一次讨论阶段计算；一次完整的实质性答复计为一次。任务完成、阻塞和验收反馈单独处理，不占讨论次数，避免讨论结束后无法交付结果。用户消息不受该上限限制。

### 方案确定与任务交接

群聊需要能区分“讨论中的建议”和“已经确认的方案”。用户敲定方案后，记录方案及分工；拥有指挥权的成员可以在授权范围内派发任务。

每项任务只需包含以下必要信息，无需完整项目管理表单：

| 信息 | 含义 |
| --- | --- |
| 战略目标与决议 | 任务服务哪个目标，依据哪项已确认方案 |
| 目标与范围 | 要完成什么，以及相关限制 |
| 任务负责人 | 谁对最终交付负责 |
| 执行者 | 哪个成员负责 |
| 验收负责人 | 完成后交给谁检查 |
| 输入与依据 | 已确认方案、相关消息及资料位置 |
| 交付物 | 需要返回的成果及存放位置 |
| 验收标准 | 如何判断完成且符合要求 |
| 授权与上报条件 | 哪些决定可以自主处理，什么情况需要用户裁决 |
| 原生会话关联 | 在哪个应用、哪个会话执行 |

执行可以继续使用绑定会话，也可以进入原生应用中新建的任务会话。是否新建属于待定产品选择；无论采用哪种方式，都必须明确关联并保留原生记录。

任务状态要区分“已交接”“执行中”和“已完成”，收到消息不等于完成工作。用户手动操作原生会话时，应避免重复投递或同时派发冲突指令。

### 原生执行与群内反馈

- 具体工作在执行者原生工具中进行，执行日志不持续刷入群聊。
- 任务应能在群聊不持续轮询发言的情况下继续执行；执行期间可继续讨论其他顶层问题。
- 完成后自动回报简明结果、交付物位置、原生会话关联、未解决问题，并 `@` 验收负责人。
- 仅在需要顶层决定、用户输入或影响任务交付时，向群聊反馈阻塞或异常。
- 首版只需显示必要状态与结果，不要求展示详细进度百分比或实时工具调用。

结果反馈示例：

> @Claude 调研已完成。结论是……；成果位于……；尚未确认的是……。请按讨论中确定的标准验收。原生任务会话：……

### 验收与返工

- 完成反馈通知指定验收负责人；其应能获得任务要求、成果位置及相关依据。
- 验收在验收者自己的工具中进行，群聊显示结论和必要依据。
- 结论至少区分“通过”“需要补充”“未通过”。执行者自报完成不等于验收通过。
- 未通过时，反馈具体缺口并 `@` 执行者；是否继续派发返工由授权范围决定。
- 返工完成后再次反馈和验收。涉及方案或范围变化时，回到群聊由用户决定。

### 追溯与轻量记录

群聊保存公共讨论、最终方案、任务分工、结果和验收结论，以及对应的原生应用会话关联。原生应用保留实际收到的任务与完整执行过程。

需要能回答：这项工作依据哪个方案、谁派发、谁执行、在哪个会话完成、谁验收、结论是什么。无需把所有执行日志复制到群聊。完成反馈应避免重复发布；连接中断或无法获得结果时，应显示未知状态，不能推断已经成功。

## 首版范围与验收

首版建议先打通用户与两个不同原生应用成员的完整流程，再扩展第三种应用。界面以群聊、成员列表、讨论控制和少量任务关联信息为主。首版能力声明只能覆盖已经验证的应用与功能。

| 验收场景 | 预期行为 |
| --- | --- |
| 用户指定一个成员回答 | 仅指定成员进入回答流程，答复出现在群里并可关联原生会话 |
| 两个成员按顺序各回复两次 | 严格按顺序进行，达到上限后不自动继续；用户可插话或结束 |
| 用户敲定方案并分工 | 保存确定的方案、执行者、验收负责人及必要任务要求 |
| 战略与任务对齐 | 每项任务关联战略目标和正式决议，能定位交付负责人 |
| 有指挥权成员派发任务 | 任务进入正确的原生应用会话；无指挥权成员的派发被阻止 |
| 分级授权与例外上报 | 授权内执行决策自主处理；超范围或战略变化反馈用户决定 |
| 原生应用执行任务 | 能使用用户直接下发同类任务时需要的原生能力，详细过程留在原生应用 |
| 执行完成 | 群里收到一次结果反馈，并正确 `@` 验收负责人；讨论次数耗尽不阻止反馈 |
| 验收后返工 | 验收者返回依据与缺口，执行者在原生工具中返工，再次交付 |
| 用户追溯或接管 | 能定位对应原生会话，查看实际任务与过程，并继续操作 |
| 应用断开或接入不等价 | 明确显示限制或失败，不静默降级、重复执行或虚报完成 |

首版成功的标准是：用户能在群里完成一次顶层决策，并看到原生工具独立执行、结果回报和负责人验收的闭环。

## 技术调研与待定事项

### 管理思想参考

以下来源用于借鉴管理原则；本文对 AI 公司角色、授权和会议流程的设计是结合用户需求的具体应用，不代表来源直接规定了这些产品功能。

- [Mission Command 与指挥意图](https://www.army.mil/article/215297/mission_command_requires_sharp_commanders_intent)：借鉴明确目的与边界、授权自主执行的思想。
- [Lean Enterprise Institute 方针管理说明](https://www.lean.org/lexicon-terms/strategy-deployment/)：借鉴战略与部门行动对齐，以及上下往返讨论可行性和资源约束的思想。
- [Amazon 2016 股东信](https://www.aboutamazon.com/news/company-news/2016-letter-to-shareholders)：借鉴决策分级、讨论后承诺执行，以及重大分歧及时升级处理的思想。

### 接入验证

MCP、原生会话接口、插件、消息通道和桌面自动化均可作为候选方式。产品需求不预先锁定技术路线。需要逐个应用确认：

1. 如何向指定原生会话投递消息并唤醒助手。
2. 如何取得答复、执行结束信号和成果关联。
3. 是否保留桌面宿主提供的全部工具和原来的权限流程。
4. 历史是否保存在原生应用，能否定位并继续使用。
5. 用户与协调层操作同一会话时，如何避免冲突。

共同上下文和群聊调度预计可保持轻量；多应用的原生会话接入与能力等价性仍是主要技术不确定性。

- [EthanSK agent-bridge](https://github.com/EthanSK/agent-bridge)：参考明确绑定会话、消息投递和回复关联机制。与 kununu 的同名项目不同。
- [Murmur](https://github.com/instavm/murmur)：参考公共消息房间、成员寻址和任务回报约定。
- [Agent Switchboard](https://github.com/FutureisinPast/mcp-agent-switchboard)：参考应用路由及不同投递能力的明确区分。

采用或复用前，需要检查当前版本、适用平台、许可证和实际会话接入方式。

### 待定产品选择

| 事项 | 当前建议或状态 |
| --- | --- |
| 群聊入口 | 待定，可为独立轻量窗口或网页；用户仍能使用原来的应用 |
| Claude 接入的具体模式 | 待确认是 Chat、Code 或 Cowork；不同模式不能混为同一能力 |
| 讨论次数统计 | 建议按讨论阶段统计，任务与验收反馈不计入 |
| 执行会话选择 | 待定，可复用绑定会话或新建原生任务会话 |
| 指挥权范围 | 建议按议题或任务授予，用户可以撤销；不默认允许转授权 |
| 自动验收启动 | 需要具备投递与唤醒能力；仅显示 `@` 提醒不足以完成闭环 |
| 应用关闭时的任务与反馈 | 待接入调研确认；原生执行持续性与协调层投递状态分别说明 |

这些选择可以在原生接入可行性明确后确定，不改变轻量讨论、原生执行、结果回报与责任验收的核心目标。
